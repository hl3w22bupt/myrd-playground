# 01 · 渲染引擎选型 与 画质/帧率策略

> 关联 ADR-001 / 002 / 003 / 005 / 007 / 008。版本事实核对于 2026-08-30（npm registry）：three `0.185.1`、vite `8.2.2`、react `19.2.8`、typescript `7.0.2`、node `26.7.0`。

## 1. 渲染引擎选型（ADR-001）

### 1.1 候选对比

| 维度 | **Three.js r185** | Babylon.js | PlayCanvas | Unity WebGL |
|---|---|---|---|---|
| 定位 | 渲染库（不规定工程结构） | 全功能引擎 | 编辑器 + 引擎 | 完整游戏引擎 |
| 核心体积（gz，约） | ~170KB | ~1MB+ | ~1MB | 10~40MB（含 wasm 堆） |
| 首屏可交互（N1 ≤5s） | ✅ 最优 | 良好 | 良好 | ❌ 难达标 |
| TS 类型 | 官方维护（three 自带） | 官方维护 | 部分 | 生成式，质量一般 |
| 内置物理/GUI/碰撞 | 无（自建） | 有 | 有 | 有 |
| 玩法逻辑自由度 | 最高（自己写 tick） | 高 | 中（受编辑器约束） | 中（C#/打包流程） |
| 生态/资料/社区 | 最大 | 第二 | 中 | 大但偏端游 |
| 免安装 Web 适配成熟度 | 最高 | 高 | 高 | 一般（加载/内存痛点） |

### 1.2 决策理由

本项目的核心工作量在**玩法仿真**（跳伞四阶段、弹道结算、缩圈几何、AI 行为、对局生命周期），而不是渲染管线。这意味着：

1. 引擎内置的"游戏框架能力"（物理引擎、GUI、场景序列化）对我们**不是收益**——跳伞/弹道/AI 全部要自己控制数值，才能满足 AC2 复现与 AC3/AC4 数值验收。
2. 引擎越"全"，越容易把逻辑写进引擎回调里，破坏"仿真与表现分离"这条主架构决策。
3. 团队成本：Three.js 的资料、示例、问题检索量最大，新人上手最快；Unity WebGL 引入 C# 工具链与打包流程，违背"关注成本"原则。
4. Unity WebGL 10~40MB 的加载体积直接违反 N1（首屏 ≤5s）。

**结论：Three.js r185 + Vite + TypeScript（5.9.x）+ 零后端。**

> 待核实项：上表体积为公开资料常见量级，非本仓库实测；立项 M0 时以实际构建产物（`vite build` + `gzip`）复核一次并回填本文档。

### 1.3 边界约定（防止"引擎漂移"）

- 渲染层**只允许** import `three`，不允许在 `render/` 之外出现 `three` 的 import（CI 用 lint 规则约束）。
- 需要自建的渲染基建（每项 <150 行）：场景对象池、LOD 管理、阴影相机跟随、毒圈/弹道特效材质、调试 HUD 覆盖层。

## 2. 帧率策略（ADR-003）

### 2.1 双循环模型

```
rAF 渲染循环（可变，浏览器驱动）
 ├── 累积器 accumulator += dt
 ├── while (accumulator >= TICK_MS && catchUp < 3)  core.tick()   // 固定 20ms = 50Hz
 ├── catchUp >= 3 → 丢弃积压并告警（不无限追赶，防止死亡螺旋）
 ├── renderer.render(scene, camera)                                 // 每帧一次
 └── render 层用 alpha = accumulator / TICK_MS 做位置插值            // 消除 50Hz 抖动
```

| 参数 | 取值 | 理由 |
|---|---|---|
| 逻辑 tick | **50Hz（20ms）** | 射击/掉血精度足够（AC4/AC5 按秒结算），比 60Hz 省 17% 逻辑开销 |
| 追加上限 | 3 tick（60ms） | 低端机掉帧时宁可画面降速，不允许逻辑雪崩 |
| 插值 | 渲染层位置/朝向 lerp，**不插值逻辑状态** | 保证回放与断言使用纯逻辑状态 |
| 帧率目标 | 桌面 60 FPS；移动 ≥30 FPS | N4 |

### 2.2 AI 与低成本项的分帧

- AI 决策每 tick 只更新 **1/4 实体**（轮转分片），单次决策耗时摊平；感知（可见性判定）与决策同频，移动每 tick 都执行。
- 毒圈掉血按秒结算（AC5 语义），在 tick 内累计时间再结算，不做逐 tick 扣血。

### 2.3 确定性与可复现（N2，直接支撑 AC2）

- 所有随机数来自 **seeded RNG（xoshiro128\*\* 或 mulberry32）**，禁止 `Math.random()`（lint 禁用）。
- 跳伞的气流扰动、AI 行为随机、物资生成都由**同一 rng 流的不同子流**驱动（`rng.fork('loot')` / `rng.fork('ai')`），避免行为改动影响物资分布。
- JS double 浮点在**同一浏览器内**完全确定 → 同机同输入序列结果一致，满足 AC2。跨设备一致性（联机 lockstep 前提）**不在本期承诺**，见 03 文档 §5。

## 3. 画质策略（三档 + 自动降档）

### 3.1 档位定义

| 参数 | Low | Medium（默认） | High |
|---|---|---|---|
| 像素比 `renderer.setPixelRatio` | `min(dpr, 1) * 0.75` | `min(dpr, 1)` | `min(dpr, 2)` |
| 阴影 | 关闭 | 1 级跟随相机（1024 map） | 2048 map + 更远投影距离 |
| 视距/雾 | 300m，雾浓 | 600m | 1200m |
| LOD 切换距离 | 收紧 50% | 基准 | 放宽 30% |
| 植被/物资实例化 | Instanced，密度 40% | 100% | 100% |
| 反锯齿 | 关 | 关（用像素比补偿） | MSAA×4（WebGL2） |
| 弹道拖尾/命中特效 | 简化（无粒子） | 完整 | 完整 |

默认档位判定：`navigator.userAgent` 粗分（移动 → Low，桌面 → Medium），High 仅手动选择或设备探测通过后开启。

### 3.2 动态降档（自动画质，实现于 render 层，与仿真无关）

- 采样窗口：每 **2 秒**计算平均 FPS 与 p95 帧时间。
- 降档：连续 2 个窗口 `FPS < 45` → 降一档（High→Medium→Low，到 Low 后改为降分辨率 25%）。
- 升档：连续 5 个窗口 `FPS > 58` → 升一档（每分钟至多一次，避免抖动）。
- 每次档位变化写入调试 HUD 与 console，便于问题定位。

### 3.3 性能预算（超预算即视为性能缺陷）

| 预算项 | 目标 | 硬上限 |
|---|---|---|
| 单帧 draw calls | < 120 | 150 |
| 单帧三角形 | < 400k | 800k |
| 逻辑 tick 单帧耗时 | < 3ms | 8ms（超限告警） |
| 首包 JS（gz） | < 800KB | 1.2MB |
| 纹理内存 | < 200MB | 400MB |

达标手段：地形/植被用 `InstancedMesh`；物资与建筑静态合批；阴影只投影主光；远处实体只更新朝向不更新动画。

### 3.4 兼容矩阵

| 平台 | 支持级别 |
|---|---|
| 桌面 Chrome / Edge（近两年版本） | 完整（High 可用） |
| 桌面 Safari / Firefox | 完整 |
| Android Chrome（中端机型，≥4GB RAM） | Low/Medium，≥30 FPS |
| iOS Safari | Low/Medium；注意 iOS 需用户手势后才能进全屏/锁定指针 |
| WebGL2 不可用 | 显示降级提示页（WebGL1 兼容不承诺，降低维护面） |

指针锁定（Pointer Lock）用于射击瞄准；用户按 `Esc` 退出属浏览器行为，UI 需提供"点击继续"重进。

## 4. 可观测性（渲染侧）

内置调试 HUD（`?debug=1` 开启，Release 默认关闭）：

- FPS / 平均与 p95 帧时间 / 逻辑 tick 耗时与漂移
- draw calls / triangles / 纹理内存（`renderer.info`）
- 实体数、AI 状态分布、当前画质档位与最近一次自动切换原因
- `?seed=123&replay=xxx`：固定种子启动、加载回放（见 02 文档 §5 事件协议）

> 验收方式：M0 完成时本 HUD 必须可用，它是后续所有性能验收的测量工具。
